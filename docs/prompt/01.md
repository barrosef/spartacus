## Decisões de Arquitetura — Projeto Spartacus

### Estrutura GCP
```
Organização GCP (CNPJ)
└── Billing Account única
    ├── Projeto GCP: spartacus-social   ← FOCO ATUAL
    └── Projeto GCP: app-comercial      ← FUTURO
```

### Stack Definida

| Camada | Tecnologia | Decisão |
|---|---|---|
| Mobile | React Native | App iOS + Android |
| Web / Backoffice | React (Vite) | SPA, usuário logado, sem necessidade de SSR/SEO |
| API / Backend | FastAPI (Python) | Cloud Run |
| Banco de dados | Firestore (NoSQL) | GCP nativo |
| Autenticação | Firebase Auth | Login social Google habilitado |
| Hospedagem frontend | Firebase Hosting | Domínio customizado + SSL automático gratuito |
| Hospedagem backend | Cloud Run | Serverless, paga só quando executa |
| Arquivos / mídia | Firebase Storage | Free tier |

### Por que essas escolhas

- **React + React Native**: máximo reaproveitamento de código entre backoffice web e mobile. Mesmos hooks, mesma lógica de negócio, mesmos padrões.
- **Firebase Hosting no lugar de Cloud Storage**: mais simples, gratuito, CDN global inclusa, domínio customizado com SSL sem configuração adicional.
- **Sem Next.js**: o backoffice é dashboard de usuário logado, sem necessidade de SEO. Next.js adicionaria complexidade sem benefício real.
- **Sem VPC**: arquitetura 100% serverless. Cloud Run + Firestore + Firebase Auth não exigem VPC. DNS é público via Cloud Run Domain Mapping + Firebase Hosting custom domain.
- **Sem Cloud DNS privado**: desnecessário no modelo serverless adotado.
- **Firebase Auth no lugar de Google Identity Platform (GCIP)**: Firebase Auth tem free tier de 10k usuários/mês. GCIP começa a cobrar com recursos enterprise. Para fase inicial, Firebase Auth é suficiente e gratuito.
- **Dois projetos GCP separados**: cada projeto tem seu próprio free tier do Firestore (1GB storage + 50k leituras/dia + 20k escritas/dia). Compartilhar um único projeto perderia esse benefício.

### DNS e Domínios

- **Backend (FastAPI no Cloud Run)**: domínio customizado via Cloud Run Domain Mapping, ex: `api.spartacus.org.br`
- **Frontend (React no Firebase Hosting)**: domínio customizado nativo do Firebase, ex: `app.spartacus.org.br` ou `spartacus.org.br`
- Sem VPC, sem Cloud DNS privado, sem Load Balancer adicional.

## Restrições e Princípios

1. **Simplicidade máxima** — sou o único desenvolvedor, sem equipe, sem budget para complexidade operacional.
2. **Custo mínimo** — priorizar free tiers. Qualquer serviço pago deve ser justificado.
3. **Sem over-engineering** — não adicionar serviços, camadas ou padrões que não sejam necessários agora.
4. **Escalabilidade futura considerada** — o projeto Spartacus eventualmente será migrado para conta organizacional própria quando o app comercial crescer. A arquitetura deve permitir isso sem grandes refatorações.
5. **Separação clara entre projetos** — nenhum recurso do Spartacus deve depender de recursos do projeto comercial futuro.

## Contexto Futuro (não implementar agora)

- Quando o app comercial for iniciado, ele terá seu próprio projeto GCP com a mesma stack.
- Em algum momento futuro, o Spartacus será migrado para uma organização GCP separada (doação da plataforma para o projeto social).
- O app comercial poderá ter VPC e infraestrutura mais robusta quando crescer — mas isso não deve contaminar as decisões atuais do Spartacus.
